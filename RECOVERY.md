# Claude TUI crash recovery (experimental)

The plugin handles interrupted native Claude interactive sessions conservatively. When tool execution or delivery is uncertain, the runtime returns HTTP 409 rather than replaying `Write`, `Edit`, `Bash`, or another client-side tool.

## Current behavior (v0.2.12 and later)

Each conversation is served from the history its request carries:

- A request that continues a live or parked native run (its tool results, or what the user said meanwhile) goes on in that native session. The safeguards and opt-in flags in the sections below apply to this path.
- Any other request — after an interruption, a client-side edit or compaction, a restart, or a run reaped after its five minutes parked on tool calls — resumes the conversation's own native transcript when the history follows it, and otherwise starts a native session rebuilt from that history. It is not refused for not matching a checkpoint.
- Tool results whose IDs do not match the tool call visible in the request's last assistant turn are still refused with HTTP 409.
- One conversation runs one native turn at a time: a second request has a 60-second wait budget and receives HTTP 503 with `Retry-After: 5` when it cannot safely proceed. Cancelling that request ends its wait; any ongoing native cleanup retains ownership until the child is reaped.
- Requests without a stable conversation id (titles, classifiers, helper calls) run stateless beside it.
- The same tool results delivered again after their reply was delivered get that reply back without a new native run — only when the whole request is identical (v0.2.13). Any other difference runs normally.
- An exhausted Claude allowance is answered with HTTP 429 (v0.2.13).
- A request larger than 32 MiB is answered with HTTP 413 `request_too_large`; compact the conversation (v0.2.14; the limit was 16 MiB before).

A rebuilt model can still *request* a tool again; this is not a general exactly-once guarantee. Check actual files before repeating `Edit`, `Write` or shell commands.

## Opt-in history import for rebuilt sessions

Install or update `github:liangxyz/claude-tui-boost` and confirm package version `0.2.20-fork.2`; this managed-JavaScript update reuses the eight platform Runtime/MCP Helper executables supplied by `0.2.20-fork.1`. Then set `MAGPIE_CLAUDE_HISTORY_IMPORT=1` in the **Magpie server process environment** to use an explicit archive when a native session must be rebuilt. The default, including `0` or an unset variable, retains structured transcript reconstruction. For an externally managed Runtime, set the variable in that Runtime's service environment. Reload at an idle boundary; the managed supervisor forwards this option as an exact `0` or `1` boolean.

The import mode starts a genuinely new native session from a user prompt. Original roles, text, thinking, tool call IDs/names/arguments, tool results and their error flags remain labelled background records. Historical tool records describe prior activity; current tool execution continues through the existing MCP handoff. The outer client's messages and checkpoint matching retain their existing representation. The `history=0` launch log counts native transcript seed entries, including when the historical records are made available through the private archive reader.

The complete rendered text includes archive records, the current task, instructions and image markers. Imports within the **512 KiB UTF-8 TUI paste budget** keep the inline first-input path. Larger imports keep their complete text in an immutable archive owned by the native run, and send a short first user prompt describing how to read it. The private `mcp__magpie__magpie_read_import_archive` tool returns indexed UTF-8 pages; its metadata identifies the byte range, page count and next page. A current request exceeding the preview budget remains complete in the archive. The prompt directs Claude to read every page before answering or acting, and permits parallel page calls. Archive reads are handled inside the Runtime and stay separate from the client's business tools.

This changes large imports from immediate text visibility to tool-mediated reading, with additional tool/model turns and latency. Text preservation and successful page delivery establish transport coverage; model comprehension and final-task success need their own evidence. The model context window and the existing **32 MiB HTTP request-body limit** still apply. Original archive pages are private to the run, while pages Claude has read enter its native transcript. A fresh native run or restart retains only the history available through its normal continuation/rebuild path.

Importing performs zero silent truncation or automatic summarization. Inline image bytes travel through the private image reader rather than the pasted prompt. URL-only images retain the existing attachment-reader refusal; supply inline image content for import mode. The default structured-transcript mode retains its existing limits.

Verified live tool handoffs keep their existing continuation path. Clean checkpoint continuations preserve native session identity and history matching; an oversized rendered current input uses the private archive reader while retaining its resume ID. The option also covers new first inputs, ordinary history rebuilds, late tool-result recovery that would otherwise create a copied session, and independent compaction sessions. Explicit tool-free recovery retains its existing input and zero-tool contract. Existing native transcripts remain intact.

This changes the model's interpretation of old assistant replies and tool traffic from native conversation turns to quoted background. Cache reuse and answer quality can therefore change. It addresses the request representation used during reconstruction; admission by a particular relay remains subject to that relay's policy and requires live verification. The option preserves historical context rather than granting permission to repeat completed tool operations.

## Busy conversations and native process cleanup

The HTTP turn claim and native-run ownership are separate. A closed client stream may still have an outstanding business tool result; the Runtime preserves that handoff. New user turns wait for the previous native turn, while matching live tool results follow the continuation path. Repeated completed tool-result requests reuse their saved answer.

Since `0.2.20-fork.1`, interactive output uses Runtime-owned pipes, with child reaping independent of waiting for a terminal transcript result. After child completion the existing bounded drain preserves available final output and closes lingering readers. This handles abnormal exits where another process keeps an output handle open. Graceful terminal-result handling and the wrapper's SIGINT cleanup opportunity remain in place. Cancellation during idle/parked teardown ends the requesting HTTP turn's wait while the native owner stays registered until cleanup completes.

A real active turn can still produce a retryable busy response. Wait for its tool work to finish or deliberately stop it before retrying. Repeated busy responses after both the native process and its tools have ended require correlated lifecycle logs; clearing saved account or checkpoint files is outside this repair.

## Managed supervisor claims and Docker process reaping

A startup error containing `already has a live supervisor claim` identifies the supervisor PID recorded in `.managed-live`. On Linux, the supervisor checks that PID's process status as well as its existence: a confirmed zombie (`Z`) or dead (`X`) process has exited, so the existing stale-claim recovery can proceed. Running processes, permission failures and unreadable or unknown status remain protected. Account ownership, connection keys and saved conversation state retain their existing checks.

Since `0.2.20-fork.2`, the shared managed-supervisor path gives each plugin host its own lightweight client connected to one account-owned Runtime supervisor. Hosts using the same saved account and normalized configuration-directory path can share that Runtime while their conversations retain separate native sessions. Use the same directory spelling across hosts, including on case-insensitive volumes. Retiring a host releases its own connection; the Runtime stays available to the remaining hosts and shuts down after the final authenticated host disconnects. Account ownership, private local IPC and the existing live claim protect attachment and Runtime startup.

The owner has an independent Unix session and detached standard streams. Startup-only coordination covers state ownership initialization and the full stale-claim recovery decision, using the existing parent's BigInt device/inode metadata. DrvFS discovery uses a private Linux location specific to the established state directory. Directory metadata selects coordination and lookup locations; the original state-path, claim and authenticated control checks continue to establish ownership. Existing per-conversation active-turn protection remains, while independent conversations run alongside each other.

A live supervisor from an earlier plugin version has no shared-attachment protocol. Let its active requests finish, then update at an idle boundary so the next startup uses the shared supervisor. Keep its claim, account directory and saved conversation state intact. During shared leases the owner keeps its Runtime endpoint; an owner failure is explicit, with automatic restart, cache recovery, endpoint migration and cross-alias attachment reserved for separate work.

Release validation used isolated Node/Bun process fixtures and 13 selected existing cases. The Node two-host scenario passed individually; the final Bun five-scenario command, final helper/frame checks and both JavaScript syntax checks exited 0. Identity derivation used fixed synthetic values and the Runtime was a local HTTP fixture. Real account authentication, native Claude inference, macOS, actual WSL/DrvFS and special-filesystem behavior remain target-environment checks. See [release notes](RELEASE_NOTES.md) for the evidence layers; the Go suite and executable builds were outside this JavaScript-only run.

For Docker deployments, enable an init process (`init: true` for the existing Compose service, or `--init` with the existing `docker run` configuration) so orphaned children are reaped. Apply this through container recreation while keeping the same `/config` bind mount and service environment. An ordinary restart keeps the current container's init setting. This addresses orphan process cleanup; the logs preceding a child exit are still needed to explain why it terminated.

When retaining a locally compiled `bin/magpie-tui-runtime`, deploy the managed lifecycle fix by updating `src/managed-runtime.mjs` and `scripts/managed-runtime-supervisor.mjs` together from the same source branch at an idle boundary. A complete plugin package update can replace that local build. These JavaScript changes use the existing Runtime binary and preserve login and conversation data.

## Checkpoint integrity and empty retries (since v0.2.8)

All checkpoint lookups validate the file at the point of use. Invalid, insecure or oversized state returns HTTP 409; it must not be treated as a new conversation. A native resume also stops if its dirty checkpoint cannot be persisted before launch. Preserve damaged state for investigation rather than deleting it to force a fresh session.

If the client resends exactly a known generated continuation followed by its synthetic error, with no new user content, removing that failed pair leaves an empty suffix. This remains a deliberate refusal and is regression-tested. A client error is not evidence that an ordinary task or tool was never executed; automatic replay remains prohibited without execution provenance.

## Known persisted-resume 502 feedback (since v0.2.8)

On a **clean, completed checkpoint**, Desktop can append an automatically generated continuation and a synthetic HTTP 502 if that continuation failed before the native Claude process started. A later ordinary user turn may then present that synthetic assistant error inside the historical suffix. The plugin can skip the strictly identified, text-only continuation/error pair; it cannot skip arbitrary error messages, old `tool_result`, model-authored responses or an ordinary user turn that failed for an unknown reason. This safety boundary deliberately prevents skipping work that might already have occurred.

The `suffix_rejected` text alone does not establish *why* the original request's history diverged. If the first error involved a real tool result, an unmatched native checkpoint, a missing live callback, or a full Desktop `/compact` rewrite, automatic seamless continuation is not guaranteed. Do not repeatedly Retry/Replay an unknown side-effecting tool. Keep the original Desktop transcript, diagnose the checkpoint and use a deliberate tool-free recovery or a new conversation after read-only verification as appropriate.

Recovery is **off by default**. Optional features include a bounded, checksummed native tool journal (`MAGPIE_CLAUDE_DURABLE_TOOL_JOURNAL=1`), guarded orphan reconstruction (`MAGPIE_CLAUDE_AUTO_RECOVER_ORPHANS=1`), and process/pane fencing (`MAGPIE_CLAUDE_NATIVE_TMUX_GUARD=1`). Optional read-only retry after a crash uses `MAGPIE_CLAUDE_AUTO_RECOVER_RETRY=1`, and first-turn dirty anchors use `MAGPIE_CLAUDE_FIRST_TURN_ANCHOR=1`. No combination of these flags authorizes replay of uncertain side effects.

The runtime uses a per-conversation native process lock inherited by the Wrapper, as well as a private tmux owner marker with the socket-environment fingerprint. If an earlier native process is still active, or its liveness cannot be proven, automatic recovery fails closed. First-turn anchors require an authentic native Session ID and a registered tool callback; completed recovery writes a new clean checkpoint.

Old conversations created before the journal/marker changes **cannot be automatically migrated**. For strictly identified exceptional cases, operators may configure a private certificate with `MAGPIE_CLAUDE_LEGACY_RECOVERY_CERT`, then use an explicit recovery request; an operator-confirmed legacy tool-result handoff has an additional `MAGPIE_CLAUDE_LEGACY_OPERATOR_APPROVED=1` gate. The one-time certificate is checked against the authenticated conversation identity, pinned native transcript, original last tool ID and content hash. It must never be shipped in a public package. A read-only reconstruction is *not* a reattachment to a previously killed MCP callback.

These features have Go tests (including real process SIGKILL and isolated tmux scenarios) and a native Claude isolated-acceptance path, but do not establish general exactly-once tool semantics or a safe migration of all existing sessions. Roll out per fresh conversation, keep backups and preserve old checkpoints and transcripts. See package tests for the expected refusal behavior.

## Historical-message changes during an MCP tool handoff (v0.2.3)

Claude Desktop may add or remove a **standalone generated token-budget reminder** inside a historical user message. A strictly recognized part, exactly matching `<system-reminder><total_tokens>N tokens left</total_tokens></system-reminder>` (including supported line-break variants), can now be normalized for live-tool continuity. User instructions, mixed reminders, tool identities and tool arguments are never normalized away. Not every three-part-to-two-part change is a token-budget notice; unrecognized edits still fail closed.

`MAGPIE_CLAUDE_AUTO_READONLY_HISTORY_DRIFT=1` optionally enables an **independent, tool-free fallback** when a live, exact-ID MCP tool-result callback reaches a changed historical prefix. The fallback requires a matching authenticated outer conversation and model, unchanged safeguards, an actively parked native run, matching canonical thread identity and a *pre-existing Dirty persistent checkpoint*. It terminates the mismatched callback and asks for one fresh read-only reconstruction with every client tool disabled. **It does not return the original tool result to the old Claude process, does not replay the command, and does not guarantee that the original interrupted Desktop turn can always be rescued.** It can spend an additional model turn and may require later manual file/result verification. The option defaults to off.

Enabling this flag is **not** a license to replay unknown `Edit`/`Write`/`Bash` side effects. If there is no exact live callback or eligible Dirty checkpoint, the runtime must still refuse unsafe continuations with HTTP 409. Previously orphaned tool results are not magically made resumable by upgrading the binary. Operator-private legacy migration certificates remain separate and are never distributed.

## Claude Desktop compaction (v0.2.4)

Claude Desktop's dedicated `/compact` request may include completed historical `tool_use` and `tool_result` blocks. The runtime recognizes the compaction protocol and writes user/assistant turns plus structured history into a **separate native Claude Code session** for a tool-free summary turn; any system prompt is included as labelled archival context. It does not replay historical tools or resume/replace the original conversation checkpoint. This only addresses the compaction request shape; unrelated 409/502 failures remain subject to the normal fail-closed behavior.

**Native input-limit diagnostic (since v0.2.9):** A failed native Claude TUI turn may write a synthetic `invalid_request` assistant row followed by `turn_duration`, without invoking the normal Stop hook. The wrapper now recognizes the completed native failure and produces a terminal error instead of waiting for Desktop to time out. The interactive Runtime preserves the original `Prompt is too long` detail and HTTP 400 status when available. This is an error-reporting fix, **not** a larger context window or a guarantee that `/compact` itself will succeed; keep the original Desktop history intact after an input-limit failure. A synthetic, tool-free integration test verifies HTTP 400 in both streaming and non-streaming paths, but it does not replace a real Claude model canary.

In the default structured-transcript mode, this separate session is seeded by writing the full source history, including tool content and images, as an additional JSONL transcript under the configured Claude profile and sending it through that profile's Claude Code authentication path. The extra local transcript can remain according to the CLI's normal session-retention behavior. With `MAGPIE_CLAUDE_HISTORY_IMPORT=1`, compaction starts a fresh native session using the same inline-or-paginated import path described above. Its private archive and image readers remain available while external client tools stay absent; the model's own context capacity still limits the summary operation. Keep the profile private and review its session files if you need to remove retained session data.

## Managed installation settings

For the normal plugin-center/automatic installation, set any of the six recovery flags above, or `MAGPIE_CLAUDE_HISTORY_IMPORT`, to exactly `1` (enable) or `0` (disable) in the **Magpie server process environment**, then reload the plugin host at an idle boundary. Values are read when that account's managed runtime starts. A shared owner retains its launch environment while authenticated clients remain. Apply new Runtime environment or executable settings at an idle boundary after all host clients release their connections and the current owner finishes cleanup; reloading one host while another holds a connection reuses the current Runtime. A client's local shell environment does not configure a Magpie server running on a VPS; services need their own service environment. Exporting a variable after Magpie has already started does not update that process.

The plugin explicitly carries these recovery flags and the history-import flag through the managed supervisor to the runtime. Missing flags remain missing; recovery and history import stay off by default. Values other than `0`/`1` and arbitrary `MANAGED_RUNTIME_EXTRA_ENV` forwarding are not accepted. API credentials and execution overrides remain scrubbed. This does not turn on recovery in the first-connect login helper.

`MAGPIE_CLAUDE_LEGACY_RECOVERY_CERT` and `MAGPIE_CLAUDE_LEGACY_OPERATOR_APPROVED` are deliberately **not** inherited by managed accounts. Exceptional legacy migration requires an operator-configured external runtime; it must never copy a private certificate or approve recovery for newly installed accounts. Do not enable every recovery flag just to match another deployment: use fresh isolated conversations and verify refusals before adopting experimental recovery.
